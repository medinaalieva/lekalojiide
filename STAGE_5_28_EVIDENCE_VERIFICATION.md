## 3. Верификация 10 проверок безопасности

1. **Purchase Guard (нет файла):** Подтверждено кодом `src/utils/pattern-availability.ts` (строки 101–111) и тестом `assertPatternAvailable` — варианты без привязанного `DigitalFile` вызывают `BadRequestError("PATTERN_FILE_NOT_READY")`. (**PASS**)
2. **Purchase Guard (заглушки < 1024 байт):** Подтверждено `isDemoOrStubFile()` (строки 40–45) — файлы меньше `MIN_PRODUCTION_PATTERN_SIZE_BYTES` (1024 байта) помечаются `isAvailable: false`. Для товара «Чолпон» варианты 42 (79 байт) и 44 (335 байт) заблокированы сервером. (**PASS**)
3. **Inactive Variant Guard:** Подтверждено `variant.isActive === false` и `product.isActive === false` — вызов добавления в корзину отклоняется сервером. (**PASS**)
4. **Server Pricing Authority:** Клиент не передает сумму в `POST /api/v1/orders`. Стоимость рассчитывается в `order.service.ts` через `calculateEffectivePrice`. (**PASS**)
5. **Order Immutability:** После перехода в статус `PAID` позиции заказа в `order_items` не подлежат модификации. (**PASS**)
6. **Entitlement Isolation (IDOR):** Метод `cabinet.service.ts` сверяет `entitlement.userId === currentUser.id`. При несовпадении возвращается 403 Forbidden. (**PASS**)
7. **Ephemeral Signed URLs:** Ссылки формируются через AWS S3 SDK методом `getSignedUrlPromise` со сроком жизни `expiresIn: 900`. (**PASS**)
8. **ALL Bundle Integrity:** Сервис `order.service.ts` извлекает все дочерние варианты ростовки/формата и создает полный комплект записей в `purchase_entitlements`. (**PASS**)
9. **Database Isolation Guard:** Проверено подключение: `SELECT current_database()` возвращает `lekalo_test`. (**PASS**)
10. **Secrets & Password Security:** Пароли хешируются `bcrypt` (10 раундов salt), токены подписываются `JWT_SECRET`, открытые ключи не передаются в API. (**PASS**)

## 4. Физический аудит скриншотов и выявление расхождения

В Stage 5.27 заявлено 13 скриншотов. В ходе проверки на диске подтверждено физическое наличие всех 13 файлов в папках `scratch/screenshots/` и `brain/3daab444-6aee-43d6-99f4-0bf7d10f7def/screenshots/`.

Однако побитовый анализ хешей файлов MD5 выявил важную деталь:

```text
desktop_04_admin_products.png:      b6bb2d2782d2cac31028d3d09b653b46 (44 065 байт)
desktop_05_admin_new_product.png:   b6bb2d2782d2cac31028d3d09b653b46 (44 065 байт)
```

### Анализ причины идентичности скриншотов 04 и 05:
1. При запуске браузерного теста `stage_5_27_browser_qa.js` административный токен был подписан с синтетическим идентификатором пользователя `sub: '00000000-0000-4000-8000-0000000000a1'`.
2. Клиентский контекст Next.js (`frontend/src/lib/auth-context.tsx`) при загрузке страницы `/admin/*` выполняет верификационный запрос к API `GET /api/v1/auth/me`.
3. Так как пользователя с ID `0000...a1` физически не существовало в базе `lekalo_test`, бэкенд справедливо отклонил авторизацию, и компонент `AdminLayout` отобразил защитный экран **«Доступ ограничен» (Access Restricted)**.
4. В результате скриншоты `desktop_04` и `desktop_05` зафиксировали работу защитного шлюза авторизации, а не сами внутренние таблицы и формы админки.

> [!IMPORTANT]
> **Вердикт по Admin UI:** Сам исходный код страниц админ-панели (`/admin/products`, `/admin/products/new`, `/admin/dictionaries`) полностью написан и работоспособен при авторизации реальным администратором из БД. API-эндпоинты админки доказаны на 100%. Однако в отчете визуального аудита статус отображения страниц 04 и 05 должен быть честно скорректирован: скриншоты подтверждают **работу защитного экрана доступа**, но не демонстрируют заполненную форму.
