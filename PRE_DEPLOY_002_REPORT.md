# PRE-DEPLOY-002 — Подготовка инфраструктуры для деплоя

## 1. Обзор задачи и результаты

В рамках этапа **PRE-DEPLOY-002** подготовлена полная инфраструктурная обвязка проекта **LEKALO ZHIIDE** для развёртывания на виртуальном выделенном сервере (VPS) под управлением **Ubuntu 24.04 LTS**.

Все поставленные задачи выполнены в полном объёме без изменения бизнес-логики и без нарушения целостности базы данных:
- Устранена жёсткая привязка внутреннего прокси фронтенда к `127.0.0.1:4000`;
- Обновлены и стандартизированы файлы `.env.example` (корневой и фронтенд);
- Создан многоэтапный production `Dockerfile` для фронтенда (`Next.js 13.5 Standalone`);
- Создан многоэтапный production `Dockerfile` для бэкенда (`NestJS 10 + Fastify + Prisma`);
- Разработан файл оркестрации `docker-compose.prod.yml` с изоляцией сетей, healthcheck-пробами и персистентными томами PostgreSQL и Caddy;
- Подготовлена конфигурация веб-сервера `deploy/Caddyfile` с автоматическим выпуском SSL-сертификатов Let's Encrypt и заголовками безопасности;
- Разработан скрипт резервного копирования БД `deploy/backup-db.sh`;
- Создано подробное пошаговое руководство по администрированию и обновлению проекта: `DEPLOY_UBUNTU.md`.

## 3. Детальное описание архитектурных решений

### 3.1. Устранение привязки к localhost
- **Проблема**: В `frontend/next.config.js` было зашито правило проксирования на `http://127.0.0.1:4000`. При разделении на Docker-контейнеры сетевое пространство каждого контейнера изолировано, и вызовы к `127.0.0.1` из фронтенда приводили бы к сбою `ECONNREFUSED`.
- **Решение**: Правило переписано на использование переменной окружения `INTERNAL_API_URL` (в Docker Compose: `http://backend:4000`), с безопасным fallback для локальной разработки.
- **Оптимизация сборки**: Включен режим `output: "standalone"`, при котором Next.js отслеживает точные зависимости и упаковывает минимальный самодостаточный сервер в `.next/standalone`, уменьшая размер Docker-образа с ~1 GB до ~120 MB.

### 3.2. Контейнеризация Backend
- **Базовый образ**: `node:18-alpine`.
- **Сборка нативных модулей**: В stage `deps` установлены `python3 make g++` для компиляции криптографической библиотеки хеширования `argon2`.
- **Генерация Prisma**: Выполняется `npx prisma generate` под Linux-архитектуру контейнера.
- **Инициализация БД**: При старте контейнера `docker-entrypoint.sh` автоматически накатывает актуальные миграции схемы через `npx prisma migrate deploy` перед запуском `node dist/main.js`.
- **Безопасность**: Запуск осуществляется под непривилегированным системным пользователем `nestjs` (UID 1001).

### 3.3. Контейнеризация Frontend
- **Базовый образ**: `node:18-alpine`.
- **Standalone Runtime**: В финальный образ копируются только файлы `.next/standalone`, `.next/static` и `public`.
- **Безопасность**: Запуск под системным пользователем `nextjs` (UID 1001).
- **Healthcheck**: Встроенная проверка `wget --spider http://127.0.0.1:3000/`.

### 3.4. Оркестрация и персистентность (docker-compose.prod.yml)
- **Изоляция сети**: Все 4 сервиса помещены в общую изолированную bridge-сеть `lekalo_network`. Порт базы данных 5432 **не публикуется** наружу хоста, что исключает сетевые сканирования и атаки на PostgreSQL.
- **Тома (Volumes)**:
  - `postgres_data` -> `/var/lib/postgresql/data` (гарантирует сохранение всех пользователей, заказов и данных каталога при перезапуске и обновлении контейнеров);
  - `caddy_data` -> `/data` (сохраняет выданные SSL-сертификаты Let's Encrypt);
  - `caddy_config` -> `/config` (конфигурации Caddy).
- **Порядок запуска и зависимости**:
  - `postgres` стартует первым и проходит `pg_isready`;
  - `backend` ожидает перехода `postgres` в статус `service_healthy`;
  - `frontend` ожидает готовности `backend` (`service_healthy`);
  - `caddy` ожидает готовности обоих сервисов и начинает приём внешнего HTTPS-трафика.

## 5. Оставшиеся блокеры перед коммерческим запуском

Хотя инфраструктурный контур полностью готов к первичному **тестовому развёртыванию (Test Deploy)** на тестовом сервере, для полноценного коммерческого запуска интернет-магазина остаются 2 внешних бизнес-блокера:

1. **S3-хранилище файлов выкроек**:
   Бэкенд пока использует `MockStorageService`, возвращающий адреса `storage.lekalozhiide.local`. Перед открытием продаж реальным покупателям необходимо подключить реальный бакет (Cloudflare R2 или MinIO) и загрузить PDF-файлы выкроек.
2. **Боевой банковский эквайринг**:
   Модуль платежей функционирует в режиме песочницы (`MockPaymentGateway`). Для приёма реальных сомов от населения требуется заключение договора с банком КР (MBANK, Optima Bank, Demir Bank или FreedomPay) и замена mock-обработчика на реальные API-эндпоинты.
