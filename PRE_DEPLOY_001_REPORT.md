# PRE-DEPLOY-001 — Подготовка LEKALO ZHIIDE к деплою

## 1. Введение и цель аудита

Настоящий отчёт представляет результаты предрелизного технического аудита готовности интернет-магазина цифровых выкроек **LEKALO ZHIIDE** к развёртыванию в production-окружении. 

Проверка охватила:
- Архитектурную целостность стека (Frontend, Backend, Database);
- Успешность компиляции production-сборок;
- Конфигурацию переменных окружения и безопасность секретов;
- Сетевые настройки (CORS, HttpOnly Cookie, JWT, localhost-привязки);
- Состояние схемы базы данных и возможность развёртывания «с нуля»;
- Статус внешних интеграций (платежи, защищённое файловое хранилище);
- Оценку рисков, расчёт стоимости хостинга и формулирование однозначного вердикта.

## 2. Текущая архитектура системы

### Компоненты стека:
1. **Frontend**:
   - Next.js 13.5.6 (App Router), React 18.2.0, TypeScript 5.3;
   - Клиентские контексты состояния: `AuthContext` (JWT + сессии), `CartContext` (локальная + серверная синхронизация);
   - Стилизация: TailwindCSS, адаптивный дизайн (Mobile/Tablet/Desktop);
   - Режимы генерации: Static Site Generation (SSG для каталога) + Dynamic SSR (для авторизованных маршрутов личного кабинета и скачивания).
2. **Backend**:
   - NestJS 10.4.15 на высокопроизводительном движке Fastify Engine (`@nestjs/platform-fastify`);
   - Аутентификация: короткоживущие Access JWT (15 мин) + ротируемые HttpOnly Refresh Cookie (30 дней), Argon2id хеширование паролей;
   - Валидация входных данных: Zod 4.6 с детальной локализацией ошибок;
   - Healthcheck: `/health` (Liveness) и `/health/ready` (Readiness с проверкой доступности PostgreSQL).
3. **Database**:
   - PostgreSQL 15/16;
   - ORM: Prisma Client 5.22.0, декларативные схемы с версионированием миграций.

## 4. Конфигурация переменных окружения

| Переменная | Назначение | Текущий статус в репозитории | Требование для Production |
|---|---|---|---|
| `NODE_ENV` | Режим работы среды | Задана (`development`) | Обязательно `production` (включает флаг Secure для cookies, строгий JWT_SECRET check) |
| `PORT` | Порт Backend API | 4000 | 4000 (или передаваемый оркестратором) |
| `DATABASE_URL` | Подключение к PostgreSQL | Присутствует в `.env` (localhost) | Пул соединений с SSL (`?sslmode=require`) к production БД |
| `JWT_SECRET` | Секретный ключ подписи токенов | Демонстрационное значение | **Критично**: минимум 32 символа, криптостойкий рандом (запрещены дефолтные слова) |
| `JWT_EXPIRES_IN` | TTL access-токена | `15m` | `15m` (рекомендовано) |
| `JWT_ISSUER` | Эмитент токенов | `lekalo-zhiide-api` | `lekalo-zhiide-api` |
| `JWT_AUDIENCE` | Аудитория токенов | `lekalo-zhiide-client` | `lekalo-zhiide-client` |
| `ALLOWED_ORIGINS` | Разрешённые веб-домены | Содержит тестовые и домен .kg | Указать только production-домены (`https://lekalo-zhiide.kg`) |
| `DEFAULT_CURRENCY` | Валюта расчётов | `KGS` | `KGS` (кыргызский сом) |
| `PAYMENT_WEBHOOK_SECRET` | Подпись вебхуков эквайринга | Зашит дефолтный mock-ключ | Секретный ключ банка-эквайера |
| `STORAGE_SIGNING_SECRET` | Подпись ссылок скачивания | Зашит дефолтный mock-ключ | Случайная 32-байтовая строка HMAC |
| `NEXT_PUBLIC_API_URL` | Базовый URL API для фронтенда | Отсутствует в `.env.example` | Необходим для SSR фронтенда (`https://lekalo-zhiide.kg` или внутренний контейнерный URL) |

> Переменные `PAYMENT_WEBHOOK_SECRET`, `STORAGE_SIGNING_SECRET` и `NEXT_PUBLIC_API_URL` в данный момент отсутствуют в файле `.env.example`. Требуется их документация.

## 5. Аудит сетевой безопасности, CORS, Cookies и JWT

1. **Привязка портов**:
   - Backend в `src/main.ts` слушает `0.0.0.0:4000`, что корректно для запуска в контейнерах Docker.
2. **CORS и CSRF**:
   - Включена проверка `isAllowedOrigin()` с защитой от спуфинга Origin и Referer.
   - Механизм `enableCors` поддерживает передачу cookie (`credentials: true`).
3. **Безопасность Cookie**:
   - Refresh-токен передаётся в `HttpOnly`-cookie, недоступном для вредоносного JS.
   - Флаг `secure` автоматически включается при `NODE_ENV === "production"`.
   - `sameSite: "lax"` обеспечивает сохранение сессии при переходе из банковского шлюза.
4. **JWT Hardening**:
   - В `src/utils/jwt.ts` встроен механизм защиты от запуска с дефолтными секретами: если `NODE_ENV === "production"` и секрет короче 32 знаков или содержит слова `default`, `example`, `change-me`, приложение аварийно завершает работу с фатальной ошибкой конфигурации.

## 8. Локальные привязки (Localhost dependencies)

Обнаружены следующие привязки к `localhost` / `127.0.0.1`, требующие параметризации перед деплоем:

1. **`frontend/next.config.js`**:
   ```javascript
   // ТЕКУЩИЙ КОД:
   destination: "http://127.0.0.1:4000/api/v1/:path*"
   ```
   *Проблема*: Если фронтенд и бэкенд будут развёрнуты в разных контейнерах или на разных хостах, `127.0.0.1` укажет на локальный сетевой стек контейнера фронтенда, где бэкенд не запущен.
   *Решение*: Заменить на `process.env.INTERNAL_API_URL || "http://backend:4000/api/v1/:path*"`.

2. **`frontend/src/lib/api.ts`**:
   ```typescript
   process.env.NEXT_PUBLIC_API_URL || "http://127.0.0.1:4000"
   ```
   *Решение*: При сборке фронтенда передавать `NEXT_PUBLIC_API_URL=https://lekalo-zhiide.kg`.

## 9. Блокеры, препятствующие безопасному деплою прямо сейчас

Перечисленные ниже 4 пункта являются абсолютными блокерами. Публикация сайта в интернет в текущем виде приведёт к неработоспособности ключевых бизнес-функций для реальных пользователей:

1. **Блокер 1 (Mock ссылки на скачивание выкроек)**:
   После оплаты клиент получает ссылку на хост `https://storage.lekalozhiide.local/...`. Этот домен не резолвится в интернете, и покупатели не смогут скачать приобретённые лекала.
2. **Блокер 2 (Хардкод адреса бэкенда в Next.js rewrites)**:
   Файл `frontend/next.config.js` завязан на `http://127.0.0.1:4000`. При раздельном контейнерном развёртывании запросы с фронтенда к API будут падать с `ECONNREFUSED`.
3. **Блокер 3 (Отсутствие реального платёжного шлюза)**:
   В системе зарегистрирован только `mock`-провайдер. Реальные платежи в сомах через MBANK / Элкарт / Visa не могут быть приняты без заключения договора с банком/эквайером и интеграции их API.
4. **Блокер 4 (Отсутствие Dockerfile и production docker-compose)**:
   В проекте отсутствуют манифесты контейнеризации для развёртывания стека в изолированном окружении Linux-сервера.

## 10. Рекомендуемый вариант инфраструктуры

### Вариант 1 (Рекомендуемый): Single VPS + Docker Compose + Caddy Reverse Proxy

Для запуска MVP интернет-магазина в Кыргызстане оптимальным решением является аренда одного виртуального выделенного сервера (VPS):

- **Сервер**: Ubuntu 24.04 LTS (2 vCPU, 4 GB RAM, 50 GB NVMe SSD).
- **Сетевая схема**:
  - **Caddy** (или Nginx): Слушает порты 80 и 443, автоматически получает бесплатный SSL-сертификат Let's Encrypt.
    - `https://lekalo-zhiide.kg` -> проксирует на `frontend:3000`;
    - `https://lekalo-zhiide.kg/api/v1/*` -> проксирует на `backend:4000`;
    - `https://lekalo-zhiide.kg/health*` -> проксирует на `backend:4000/health*`.
  - **Docker Compose сеть**: Все сервисы (`frontend`, `backend`, `db`, `caddy`) общаются по внутренней изолированной сети без открытия порта БД наружу.
- **Хранилище файлов (PDF выкройки)**:
  - **Cloudflare R2** (S3-совместимое): Бесплатный тариф включает 10 ГБ хранилища и 0$ за исходящий трафик (Egress), что критично для цифровых файлов большого объёма.
- **Локация сервера**:
  - Казахстан (Алматы) или Германия/Финляндия (Hetzner). Пинг из Бишкека и регионов Кыргызстана: 15–70 мс.

## 11. Конкретная последовательность следующих действий

1. **Шаг 1 (Конфигурация параметров сборки)**:
   - Параметризовать `frontend/next.config.js` через `process.env.INTERNAL_API_URL`.
   - Дополнить `.env.example` недостающими переменными (`NEXT_PUBLIC_API_URL`, `STORAGE_SIGNING_SECRET`, `PAYMENT_WEBHOOK_SECRET`).
2. **Шаг 2 (Создание контейнеризации)**:
   - Создать `Dockerfile` для backend (Multi-stage build на базе `node:18-alpine`);
   - Создать `Dockerfile` для frontend (`next build` в `standalone` режиме);
   - Создать `docker-compose.prod.yml` с сервисами `db`, `backend`, `frontend` и `caddy`.
3. **Шаг 3 (Реализация Production Storage Adapter)**:
   - Реализовать S3-совместимый адаптер (AWS SDK v3 / `@aws-sdk/client-s3`) для Cloudflare R2 / MinIO вместо MockStorageService.
4. **Шаг 4 (Подготовка к подключению платёжного шлюза)**:
   - Оставить для закрытого предрелизного тестирования переключатель `PAYMENT_GATEWAY=mock`, но подготовить модуль к внедрению реального API банка (MBANK/Optima).
5. **Шаг 5 (Развёртывание на сервере)**:
   - Арендовать VPS, привязать DNS-запись домена, выполнить `docker compose -f docker-compose.prod.yml up -d`, применить миграции `prisma migrate deploy` и сиды `prisma db seed`.

## 12. Итоговый вывод

# NOT READY FOR DEPLOY

### Обоснование вердикта:
Несмотря на то, что программный код фронтенда и бэкенда полностью компилируется, типы проверены, а база данных имеет актуальную схему, проект **не готов к публичному релизу** из-за 4 критических блокеров:
1. Выдача ссылок на файлы выкроек завязана на несуществующий локальный хост (`storage.lekalozhiide.local`);
2. Внутренний прокси Next.js жестко привязан к `127.0.0.1:4000`;
3. Отсутствуют production-манифесты контейнеризации (`Dockerfile` / `docker-compose.prod.yml`);
4. Онлайн-оплата функционирует исключительно в Mock-песочнице.

Переход к деплою возможен сразу после устранения блокеров конфигурации и создания docker-окружения.
