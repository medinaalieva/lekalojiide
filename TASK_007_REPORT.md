## 1. Обзор выполненной работы

В рамках задачи **TASK-007** полностью реализованы модули корзины (`CartModule`) и оформления заказов (`OrdersModule`) для интернет-магазина цифровых выкроек **LEKALO ZHIIDE**.

Реализация строго опирается на существующую архитектурную документацию (`docs/architecture/ARCHITECTURE.md`), спецификацию API (`docs/architecture/API_SPECIFICATION.md`) и схему данных (`prisma/schema.prisma`).

### Ключевая функциональность

1. **Корзина покупателя (`CartModule` / `/api/v1/cart/*`)**:
   - Получение текущей корзины авторизованного покупателя (`GET /api/v1/cart`) с ленивым созданием при первом обращении.
   - Серверный расчёт цен позиций и общей суммы в сомах (`KGS`) с учётом переопределения цен вариантов (`priceOverride`) и базовой цены товара (`basePrice`), исключая ошибки округления IEEE 754.
   - Добавление товара в корзину (`POST /api/v1/cart/items`):
     - Проверка существования выкройки и варианта.
     - Запрет добавления неопубликованных выкроек (`isActive: false` -> HTTP 400 `PRODUCT_INACTIVE`).
     - Запрет добавления неактивных вариантов (`isActive: false` -> HTTP 400 `VARIANT_INACTIVE`).
     - Проверка соответствия варианта товару (`variant.productId === productId`).
     - Защита от дубликатов: попытка повторного добавления того же варианта отклоняется с HTTP 409 `VARIANT_ALREADY_IN_CART`.
   - Изменение выбранного варианта в корзине (`PUT /api/v1/cart/items/:id`) (например, изменение размера или формата выкройки) с автоматическим пересчётом стоимости.
   - Удаление отдельной позиции (`DELETE /api/v1/cart/items/:id`).
   - Полная очистка корзины (`DELETE /api/v1/cart`).
   - Строгая изоляция: покупатель имеет доступ только к своей корзине; попытка манипуляции чужими позициями возвращает HTTP 404.

2. **Оформление заказов (`OrdersModule` / `/api/v1/orders/*`)**:
   - Транзакционный чекаут (`POST /api/v1/orders/checkout`) в рамках единой ACID-транзакции `prisma.$transaction`:
     1. Проверка авторизации покупателя.
     2. Получение актуальной корзины из PostgreSQL.
     3. Запрет оформления пустой корзины (HTTP 422 `CART_EMPTY`).
     4. Повторная серверная валидация доступности и активности каждого товара и варианта на момент покупки.
     5. Серверный расчёт финальной суммы в валюте KGS.
     6. Генерация уникального номера заказа по шаблону `LZ-YYYY-XXXXXXXX`.
     7. Фиксация неизменяемого снимка данных (`productSnapshot`) в `OrderItem` (название, артикул SKU, размер, рост, формат, цена на момент покупки).
     8. Атомарная очистка корзины только после успешной фиксации заказа.
     9. Гарантия отката: при любой ошибке корзина остаётся нетронутой, частичный заказ не создаётся.
   - Просмотр списка заказов текущего покупателя (`GET /api/v1/orders`).
   - Детальный просмотр конкретного заказа (`GET /api/v1/orders/:id`) с проверкой прав владения (доступ покупателя к чужому заказу блокируется с HTTP 403 `FORBIDDEN`).

3. **Административное управление заказами (`OrdersAdminController` / `/api/v1/admin/orders/*`)**:
   - Защита через RBAC: доступ строго ограничен ролями `ADMIN` и `CONTENT_MANAGER`.
   - Просмотр всех заказов магазина (`GET /api/v1/admin/orders`) с пагинацией и фильтрацией по статусу (`OrderStatus`) и email покупателя.
   - Детальный просмотр любого заказа (`GET /api/v1/admin/orders/:id`) с данными пользователя, снимками позиций и суммами.

## 3. Спецификация API

### 3.1. Корзина (`/api/v1/cart`) — Клиентский API
*Требует заголовок `Authorization: Bearer <token>`.*

| Метод | Путь | Описание | Код ответа |
|---|---|---|---|
| `GET` | `/api/v1/cart` | Получение корзины покупателя с расчётом суммы | `200 OK` |
| `POST` | `/api/v1/cart/items` | Добавление варианта выкройки в корзину | `201 Created` |
| `PUT` | `/api/v1/cart/items/:id` | Смена выбранного варианта выкройки | `200 OK` |
| `DELETE` | `/api/v1/cart/items/:id` | Удаление позиции из корзины | `200 OK` |
| `DELETE` | `/api/v1/cart` | Полная очистка корзины | `200 OK` |

### 3.2. Заказы (`/api/v1/orders`) — Клиентский API
*Требует заголовок `Authorization: Bearer <token>`.*

| Метод | Путь | Описание | Код ответа |
|---|---|---|---|
| `POST` | `/api/v1/orders/checkout` | Оформление заказа из корзины | `201 Created` |
| `GET` | `/api/v1/orders` | Список заказов текущего покупателя | `200 OK` |
| `GET` | `/api/v1/orders/:id` | Детальный просмотр своего заказа | `200 OK` |

### 3.3. Административный API заказов (`/api/v1/admin/orders`)
*Требует заголовок `Authorization: Bearer <token>` и роль `ADMIN` или `CONTENT_MANAGER`.*

| Метод | Путь | Описание | Код ответа |
|---|---|---|---|
| `GET` | `/api/v1/admin/orders` | Список всех заказов с пагинацией и фильтрами | `200 OK` |
| `GET` | `/api/v1/admin/orders/:id` | Детальная информация о любом заказе | `200 OK` |

## 4. Состояние базы данных и Prisma Schema

Существующая схема `prisma/schema.prisma` полностью и без изменений покрыла все потребности функционала:
- Модели `Cart` и `CartItem` с уникальным индексом `@@unique([cartId, productVariantId])` гарантируют отсутствие дубликатов позиций.
- Модели `Order` и `OrderItem` со статусами перечисления `OrderStatus` (`PENDING`, `PAID`, `CANCELLED` и др.) и полем `productSnapshot Json` обеспечивают неизменяемость истории заказов.
- Дополнительных миграций базы данных не потребовалось (`Database schema is up to date!`).
