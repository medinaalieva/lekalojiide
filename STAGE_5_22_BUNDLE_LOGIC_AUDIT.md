# STAGE 5.22: BUNDLE LOGIC AUDIT
## Комплексный аудит логики покупки полного размерного ряда (ALL / Bundle)

**Проект:** LEKALO ZHIIDE  
**Дата аудита:** 19 ноября 2026 г.  
**База данных:** `lekalo_test` (Neon Serverless PostgreSQL)  
**Режим:** READ-ONLY / AUDIT & ENHANCEMENT  
**Статус:** Решено и верифицировано  

---

## 1. Введение и цели исследования

В проекте LEKALO ZHIIDE для моделей одежды предусмотрена возможность приобретения не только отдельного размера (например, 42, 44, 46 и т.д.), но и полного комплекта лекал всех доступных размеров для выбранного роста и формата печати («Все размеры / Комплект»).

Данный аудит решает задачу комплексной верификации архитектуры покупки комплекта:
1. Как концепция комплекта представлена в реляционной модели данных (`Product`, `ProductVariant`, `Size`).
2. Как генерируются и поддерживаются варианты `ALL`.
3. Как формируется ценообразование (`bundlePrice`, `priceOverride`, скидки).
4. Как Purchase Availability Guard защищает покупателя от покупки не готовых комплектов.
5. Как корзина и заказ сохраняют целостность и неизменность цены (Order Snapshot).
6. Как платёжный вебхук выдаёт права доступа (`PurchaseEntitlement`) на все дочерние размеры комплекта.
7. Как витрина магазина отображает переключатель «Все размеры» и исключает отображение фантомных комплектов.

## 2. Архитектурное исследование сквозного цикла покупки

### 2.1. Модель данных (Database Schema)

В схеме данных Prisma комплект не является отдельной «виртуальной сущностью» без связей. Он полностью интегрирован в общую систему каталога:

1. **Таблица `sizes`:**
   В таблице существует системная запись с кодом `'ALL'`:
   - `id`: `3045e56c-b073-4eac-a7ae-f59e4a9605c0`
   - `code`: `'ALL'`
   - `label`: `'Все размеры (комплект)'`
   - `sortOrder`: `999` (всегда замыкает список размеров)
   - `isActive`: `true`

2. **Таблица `products`:**
   Каждый товар содержит два конфигурационных флага:
   - `hasBundleOption` (`Boolean`, default: `false`) — признак доступности комплекта для товара.
   - `bundlePrice` (`Decimal(10,2)`, nullable) — базовая фиксированная стоимость комплекта.
   - `basePrice` (`Decimal(10,2)`) — базовая цена отдельного размера.

3. **Таблица `product_variants`:**
   Комплект создается как полноценная запись `ProductVariant`:
   - `productId` → указывает на товар.
   - `sizeId` → указывает на системный размер `ALL`.
   - `heightId` → конкретный рост (например, 164-170).
   - `formatId` → конкретный формат (например, A4 или Плоттер).
   - `sku` → канонический SKU вида `${prefix}-ALL-${height}-${format}` (например, `LZ-CHOLPON-ALL-164-170-A4`).
   - `priceOverride` → опциональная переопределенная цена комплекта.

### 2.2. Генерация вариантов (Catalog Service & Admin UI)

Ранее в системе генерация вариантов `ALL` не была автоматизирована в `batchGenerateVariants`. В результате из 23 товаров каталога только 1 товар (`LZ-AIDA`) имел запись `ALL` в базе данных, а для остальных 22 товаров при включенном `hasBundleOption: true` варианты отсутствовали.

**Внедренное решение (Stage 5.22):**
- В схему `BatchVariantsSchema` добавлен флаг `includeBundle?: boolean`.
- В методе `CatalogService.batchGenerateVariants`:
  1. Если `includeBundle === true`, либо `includeBundle !== false` и у товара включен `hasBundleOption === true` и задана `bundlePrice !== null`, сервис находит системный размер `ALL`.
  2. Для каждой комбинации выбранных ростов (`heightIds`) и форматов (`formatIds`) сервис выполняет идемпотентный `upsert` варианта с кодом `ALL`:
     - SKU: `${prefix}-ALL-${heightLabel}-${formatLabel}`
     - `isActive`: `true`
  3. Если комплект не выбран (`includeBundle === false`), все существующие `ALL`-варианты для данного товара деактивируются (`isActive: false`).
- В методе `CatalogService.updateProduct`:
  - При переключении флага `hasBundleOption` статус активности (`isActive`) всех вариантов с размером `ALL` синхронно обновляется.

### 2.3. Ценообразование (Pricing Calculation)

Ценообразование комплекта рассчитывается детерминированно функцией `calculateEffectivePrice`:
1. Если у варианта задан `priceOverride > 0` — применяется `priceOverride`.
2. Если `size.code === 'ALL'` и у товара задан `bundlePrice > 0` — применяется `bundlePrice`.
3. Иначе применяется `basePrice` товара.

**Пример для «Пальто оверсайз Чолпон»:**
- Одиночный размер: `basePrice = 350 сом`.
- Комплект из 6 размеров (40, 42, 44, 46, 48, 50): `bundlePrice = 1750 сом`.
- Экономия покупателя: `6 * 350 - 1750 = 2100 - 1750 = 350 сом` (1 размер бесплатно).

### 2.4. Защита покупки: Purchase Availability Guard

Критический аспект: **конструктивные PDF-выкройки загружаются конструктором на конкретные размеры** (например, `palto-cholpon-42-164-170-A4.pdf`). Вариант `ALL` не имеет отдельного составного PDF, если только конструктор не загрузит специальный единый архив/PDF.

Если бы `Purchase Guard` проверял только прямые файлы варианта `ALL`, произошла бы одна из двух ошибок:
- **Ложное блокирование:** покупатель не мог бы купить комплект, даже если все 6 размеров готовы.
- **Ложное открытие:** покупатель мог бы купить комплект, когда ни один файл не готов.

**Реализованная двухуровневая логика Purchase Guard:**
```typescript
// src/utils/pattern-availability.ts
if (isBundle) {
  // 1. Если для самого варианта ALL загружен валидный файл (прямой составной PDF)
  if (variantFileResult.available) {
    return { available: true };
  }

  // 2. Иначе проверяем готовность ВСЕХ активных дочерних размеров того же роста и формата
  if (!childVariants || childVariants.length === 0) {
    return {
      available: false,
      reason: 'PATTERN_FILE_NOT_READY',
      message: 'Выкройки для данного комплекта ещё готовятся конструктором.',
    };
  }

  // Проверяем каждый дочерний размер
  for (const child of childVariants) {
    const childResult = checkSingleVariantFile(child);
    if (!childResult.available) {
      return {
        available: false,
        reason: 'PATTERN_FILE_NOT_READY',
        message: 'Не все размеры из комплекта готовы. Выкройка готовится конструктором.',
      };
    }
  }

  return { available: true };
}
```

**Критерии готовности дочернего размера:**
1. Наличие активного `DigitalFile` типа `PATTERN`.
2. Наличие записи `FileVersion`.
3. Размер файла `fileSizeBytes >= 1024` байт (отсекает 5-байтовые DEMO-заглушки).
4. Имя файла не содержит маркер заглушки `demo-stub-pattern.pdf`.

Если хотя бы один размер из размерной сетки не загружен конструктором или является заглушкой — покупка комплекта **строго блокируется**.

### 2.5. Корзина и заказ (Cart, Checkout & Order Snapshot)

1. **Добавление в корзину (`CartService.addItem`):**
   При добавлении варианта `ALL` сервис находит все активные дочерние размеры товара для соответствующего `heightId` и `formatId`, и передает их в `assertPatternAvailable`. Не готовый комплект отклоняется с HTTP 400 `PATTERN_FILE_NOT_READY`.
2. **Получение корзины (`CartService.getUserCart` / `formatCart`):**
   Каждая позиция корзины содержит динамический флаг `isAvailable`. Если файл одного из размеров был деактивирован после добавления в корзину, флаг становится `false`.
3. **Оформление заказа (`OrdersService.createOrder`):**
   Перед созданием заказа сервис повторно загружает дочерние варианты для всех позиций корзины и выполняет `assertPatternAvailable`. При отказе заказ не создается, транзакция откатывается, корзина сохраняется в неизменном виде.
4. **Order Snapshot:**
   В позицию заказа (`OrderItem`) сохраняются неизменяемые данные:
   - `priceAtPurchase`: зафиксированная цена комплекта на момент заказа (`bundlePrice`).
   - `variantSnapshot`: замороженный JSON со всеми характеристиками (название, SKU, рост, формат, код размера `'ALL'`).

### 2.6. Оплата и выдача прав (Webhook & Customer Library)

При поступлении вебхука от платежного шлюза (`PaymentsService.handleWebhookEvent` со статусом `payment.succeeded`):
1. Заказ переходит в статус `PAID`.
2. Для каждого `OrderItem`:
   - Если позиция — обычный вариант: создается одна запись `PurchaseEntitlement` на этот вариант.
   - **Если позиция — вариант `ALL` (размер `ALL`):**
     Сервис находит все активные дочерние варианты товара с тем же `heightId` и `formatId`.
     Для каждого дочернего размера создается отдельный `PurchaseEntitlement`:
     ```typescript
     await prisma.purchaseEntitlement.create({
       data: {
         userId: order.userId,
         orderId: order.id,
         variantId: child.id,
         status: 'ACTIVE',
       },
     });
     ```
   - Если для самого `ALL`-варианта загружен прямой файл (например, объединенный PDF), на него также выдается `PurchaseEntitlement`.
3. **Личный кабинет (`CabinetService.getMyLibrary`):**
   Покупатель открывает раздел «Мои выкройки» и видит доступ к скачиванию **каждого размера из купленного комплекта**. Ссылки на скачивание формируются через безопасный `CabinetService.getDownloadUrl` с верификацией прав и проверкой HMAC/S3 Presigned URL.

## 3. Матрица покрытия сценариев

| Сценарий | Описание | Ожидаемый результат | Статус аудита |
|---|---|---|---|
| **SC-1** | Генерация вариантов с `hasBundleOption = true` | Создаются `ALL` варианты для всех выбранных ростов и форматов | **ПОДТВЕРЖДЕНО** |
| **SC-2** | Идемпотентность повторной генерации | Повторный вызов обновляет существующие записи без дубликатов | **ПОДТВЕРЖДЕНО** |
| **SC-3** | Генерация для товара без комплекта | Варианты `ALL` не создаются | **ПОДТВЕРЖДЕНО** |
| **SC-4** | Расчет стоимости комплекта | Применяется `bundlePrice` со скидкой, сохраняется в Order Snapshot | **ПОДТВЕРЖДЕНО** |
| **SC-5** | Защита от покупки без файлов (Purchase Guard) | 400 `PATTERN_FILE_NOT_READY` при отсутствии реальных файлов | **ПОДТВЕРЖДЕНО** |
| **SC-6** | Успешное добавление в корзину при готовых PDF | 201 Created при наличии валидных файлов у всех дочерних размеров | **ПОДТВЕРЖДЕНО** |
| **SC-7** | Блокировка чекаута при неготовом комплекте | Чекаут блокируется с 400 `PATTERN_FILE_NOT_READY` | **ПОДТВЕРЖДЕНО** |
| **SC-8** | Атомарность отказа и сохранение корзины | Заказ не создается, корзина пользователя сохраняется | **ПОДТВЕРЖДЕНО** |
| **SC-9** | Выдача прав на все размеры комплекта после оплаты | Создаются `PurchaseEntitlement` для каждого дочернего размера | **ПОДТВЕРЖДЕНО** |
| **SC-10** | Защита от несанкционированного доступа | Не купленные размеры или форматы недоступны для скачивания (403 Forbidden) | **ПОДТВЕРЖДЕНО** |

## 4. Выводы аудита

1. Архитектура комплектов полностью соответствует бизнес-требованиям владельца: покупатель платит фиксированную цену за комплект и получает доступ ко всем размерам купленного роста и формата.
2. Исключены риски продажи «пустых» комплектов: Purchase Availability Guard гарантирует, что кнопка «Купить» и чекаут активны только тогда, когда конструктор предоставил реальные производственные файлы для всех заявленных размеров.
3. Кодовая база протестирована и готова к приему производственных PDF от конструктора.
