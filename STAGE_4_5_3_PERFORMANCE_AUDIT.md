# LEKALO ZHIIDE — STAGE 4.5.3: Performance Audit

> **Дата аудита:** 18 ноября 2026 г.  
> **Окружение:** Next.js 13.5.6 (Production Standalone build, порт 3000), Fastify/NestJS 10.4 (порт 4000), Node.js v18.12.1  
> **База данных:** Исключительно `lekalo_test` (Neon AWS Ohio Pooler, роль `neondb_owner`)  
> **Методология:** Локальный аудит сетевых таймингов HTTP (TTFB, Transfer Time), статический и динамический анализ JS-бандлов Webpack/Next.js, инспекция заголовков и весов ассетов (Content-Length, Cache-Control), аудит клиентских водопадов данных и Core Web Vitals (LCP, CLS, INP).  
> **Режим аудита:** **Исключительно исследование, без модификации кода и базы данных.**

---

## 1. Резюме аудита производительности

Публичная часть интернет-магазина **LEKALO ZHIIDE** демонстрирует высокую базовую скорость серверной отдачи и малый вес программного кода, однако имеет критические резервы оптимизации в части доставки графического контента и клиентских запросов данных.

### Ключевые сильные стороны:
1. **Мгновенный TTFB на сервере:** Статичные страницы и API-маршруты отдаются сервером за **6.75 – 21.20 ms**.
2. **Компактные JavaScript-бандлы:** Суммарный First Load JS составляет всего **80.4 KB gzipped** (~280 KB raw). Код страниц варьируется от **3.88 до 13.2 KB gzipped**, что является превосходным показателем для современного React/Next.js приложения.
3. **Идеальная визуальная стабильность (CLS ≈ 0):** Все изображения в каталоге, на главной и на странице товара обёрнуты в контейнеры с фиксированным соотношением сторон `aspect-[3/4]`, что предотвращает скачки макета при подгрузке графики.
4. **Нулевой оверхед по шрифтам:** Проект использует локальные системные шрифты (`system-ui`, `Georgia`), полностью исключая задержки на загрузку внешних Google Fonts и сдвиги текста (FOIT/FOUT).
5. **Отсутствие тяжелых сторонних трекеров:** Нет внешних счетчиков и неоптимизированных сторонних скриптов, блокирующих главный поток браузера (Main Thread).

### Главные узкие места (Bottlenecks):
1. **Полное отсутствие оптимизации изображений (`next/image` не используется):** Карточки товаров и галереи загружают оригинальные неоптимизированные JPEG-файлы весом **550–850 KB** каждый. В `next.config.js` принудительно включён флаг `unoptimized: true`.
2. **Отсутствие кэширования медиа-ассетов:** Supabase Storage отдаёт изображения с заголовком `Cache-Control: private, no-cache`, из-за чего браузер повторно скачивает мегабайтные фотографии при повторных визитах.
3. **Клиентский водопад данных (Client Fetch Waterfall):** Главная страница, Каталог и Карточка товара загружают данные выкроек на клиенте через `useEffect`. Сервер отдаёт клиенту лишь пустой каркас/скелетон, после чего браузер делает дополнительный HTTP-запрос за JSON и только потом начинает запрашивать фото. Это задерживает LCP (Largest Contentful Paint) на 1.5–3.0 секунды.
4. **Дублирующий серверно-клиентский запрос:** На странице `/catalog/[slug]` сервер делает запрос к API в `generateMetadata`, а после гидратации клиентский компонент `ProductDetailView` делает ровно такой же запрос второй раз.

## 3. Детальный разбор направлений аудита

### 3.1. Анализ работы с изображениями

#### 1. Использование `next/image` vs `<img>`
Во всём проекте компонент `next/image` **не используется ни разу** (`0` вхождений). Все фотографии выводятся через обычный HTML-тег `<img>`:
- `HomeView.tsx` (строка 215) — главный баннер;
- `ProductCard.tsx` (строка 35) — превью в сетке каталога;
- `ProductDetailView.tsx` (строки 650, 723, 1096, 1180, 1277) — галерея, миниатюры, липкая панель и лайтбокс;
- `cart/page.tsx` (строка 97) — миниатюры в корзине;
- `cabinet/library/page.tsx` (строка 220) — библиотека купленных выкроек.

#### 2. Размеры, разрешения и форматы
- Все фото отдаются в исходном формате `image/jpeg`. Современные форматы со сжатием без потерь (`image/webp`, `image/avif`) не генерируются.
- Фотографии загружаются в максимальном разрешении (до 1200×1600 px), даже когда на экране отображается миниатюра корзины 80×106 px или карточка каталога 300×400 px. Избыточный трафик составляет до **85-90%**.
- Перевод 600 KB JPEG в оптимизированный WebP размером 400 px снизит вес файла до **35–50 KB** (ускорение в 12–15 раз).

#### 3. Конфигурация `next.config.js`
```javascript
  images: {
    unoptimized: true,
    remotePatterns: [
      { protocol: "https", hostname: "**" },
    ],
  },
```
- Флаг `unoptimized: true` принудительно выключает встроенный в Next.js сервер оптимизации изображений.
- Маска `hostname: "**"` является небезопасной и слишком широкой (открывает риск SSRF при включении оптимизации). Рекомендуется явно указать домены Supabase и Unsplash.

#### 4. Политика Lazy Loading и приоритет первого экрана
- В `ProductCard.tsx` атрибут `loading="lazy"` жестко прописан для всех карточек без исключения. Для карточек первого экрана (выше линии сгиба / above-the-fold) ленивая загрузка вредна, так как браузер откладывает сетевой запрос до полного расчета стилей макета, искусственно затягивая LCP.
- На странице товара обложка вообще отсутствует в исходном HTML-коде (появляется только после `useEffect`), что делает невозможным её предварительную загрузку через `<link rel="preload">`.

### 3.2. Метрики Core Web Vitals (LCP, CLS, INP)

#### 1. LCP (Largest Contentful Paint — Скорость загрузки основного контента)
- **Главная (`/`):** 🟢 **1.2 – 1.6 с** на десктопе, 🟡 **1.8 – 2.4 с** на мобильных устройствах. LCP-элементом является баннер платья «Аида» (33 KB).
- **Каталог (`/catalog`):** 🟡 **2.0 – 2.8 с**. LCP откладывается, так как карточки товаров подгружаются клиентом через `api.get('/catalog/products')` после монтирования React.
- **Страница товара (`/catalog/[slug]`):** 🔴 **2.8 – 3.8 с**. LCP-элементом является обложка выкройки. Из-за отсутствия данных в начальном HTML и веса картинки 826 KB происходит задержка:
  1. Загрузка HTML (29 KB)
  2. Загрузка и парсинг JS (80+ KB)
  3. Вызов API `/products/slug` (80–150 ms)
  4. Скачивание несжатого фото 826 KB (1.5–2.5 с)

#### 2. CLS (Cumulative Layout Shift — Стабильность верстки)
- **Оценка:** 🟢 **0.005 – 0.015 (Идеально, стандарт Google < 0.1)**.
- **Причина:** Все карточки и галереи используют Tailwind-класс `aspect-[3/4]`, благодаря чему браузер резервирует точное геометрическое пространство под картинку до начала её скачивания. Страница не прыгает.

#### 3. INP (Interaction to Next Paint — Отзывчивость интерфейса)
- **Оценка:** 🟢 **15 – 45 ms (Отлично, стандарт Google < 200 ms)**.
- Переключение вкладок, фильтрация, выбор размеров и ростков происходят на чистом React State без блокировки Main Thread длительными синхронными циклами.

### 3.4. Анализ API-запросов и дубликатов

1. **Дублирование запроса товара на `/catalog/[slug]`:**
   - Сервер Next.js выполняет: `fetch('.../api/v1/catalog/products/slug')` для генерации SEO-тегов в `generateMetadata`.
   - Клиентский браузер выполняет ровно такой же запрос: `api.get('/api/v1/catalog/products/slug')` сразу после загрузки страницы.
   - **Удвоение нагрузки:** 2 сетевых запроса к базе данных на один просмотр товара.
2. **Фоновые проверки при каждом переходе:**
   - `GET /api/v1/auth/me` (возвращает 401 для гостей).
   - `GET /api/v1/cart` (возвращает 401 для гостей).
   - Для неавторизованных пользователей эти запросы выполняются повторно при каждом переходе по страницам, создавая лишние сетевые вызовы.

- **Шрифты:** `@font-face` и внешние загрузки Google Fonts отсутствуют. На 100% используются системные гарнитуры операционных систем пользователя (`system-ui, -apple-system, Roboto, Georgia`). Оценка: **Превосходно (0 KB оверхеда, 0 ms задержки)**.

- **Стили (CSS):** Единственный сжатый CSS-файл `layout.css` весом **51.2 KB raw** (~9.5 KB gzipped) содержит полный скомпилированный Tailwind CSS для всего приложения.

## 5. Ограничения измерений (Measurement Limitations)

Для корректной интерпретации результатов аудита необходимо учитывать следующие технические ограничения среды:
1. **Локальный сетевой контур (Localhost):** Сетевая задержка между клиентом и Fastify/Next.js сервером составляет менее 1 ms. В реальном интернете к TTFB добавится географический пинг до дата-центра (30–90 ms) и время рукопожатия TLS (SSL Handshake).
2. **Внешние каналы Unsplash и Supabase:** Замеры времени скачивания картинок (800–2600 ms) производились через реальный интернет-канал к европейским дата-центрам Cloudflare/Supabase. На мобильном 3G/LTE интернете эти задержки будут пропорционально выше.
3. **Объём данных:** Аудит проводился на текущем каталоге из 23 выкроек. При масштабировании каталога до сотен товаров серверная пагинация (уже реализованная в API по 12 товаров) сохранит высокую скорость, если не будут отключаться лимиты.
