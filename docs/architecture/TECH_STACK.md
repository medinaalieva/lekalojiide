## 1. Сравнение базовых архитектурных подходов

Перед выбором конкретных библиотек и фреймворков сопоставлены две фундаментальные парадигмы организации проекта:

- **Архитектура А (Раздельная: Next.js + NestJS + PostgreSQL + Prisma)**: Frontend (BFF / SSR витрина на Next.js) и Backend (отдельный API-сервис на NestJS) разделены физически и логически.
- **Архитектура Б (Монолитная: Next.js Fullstack + PostgreSQL + Prisma)**: Единое приложение Next.js, где публичная витрина, серверная логика (Server Actions, Route Handlers), личный кабинет и админка находятся в рамках одного проекта.

### 1.1. Детальная матрица сравнения

| Критерий оценки | Вариант А: Next.js (Front) + NestJS (API) | Вариант Б: Next.js Fullstack (Server Actions / Route Handlers) |
| :--- | :--- | :--- |
| **1. Сложность разработки (Development Complexity)** | **Выше средней**. Требуется настройка двух приложений, общих типов через DTO/OpenAPI или shared-пакет в монорепозитории. NestJS требует знания паттернов Dependency Injection, модулей и декораторов. | **Низкая / Средняя**. Единый проект, прямой импорт типов Prisma в серверные компоненты и Server Actions. Быстрый старт, меньше бойлерплейта на первом этапе. |
| **2. Стоимость поддержки и хостинга (Maintenance & Infra)** | **Умеренная**. Требуется запуск двух Node.js сервисов (Next.js SSR и NestJS API), настройка единого прокси Nginx и двух наборов конфигураций. | **Минимальная**. Единый Docker-контейнер или развертывание на VPS. Меньше накладных расходов на сопровождение инфраструктуры на этапе MVP. |
| **3. Масштабируемость (Scalability)** | **Отличная**. Нагрузка на рендеринг публичных страниц витрины (SSR) изолирована от API-сервера, обрабатывающего платежные вебхуки, корзину и генерацию ссылок на файлы. Сервисы масштабируются независимо. | **Ограниченная**. При высокой нагрузке на SSR витрины ресурсы процессора и пулы соединений к БД делятся с критическими процессами обработки заказов и вебхуков. |
| **4. Безопасность (Security)** | **Максимальная**. Бэкенд-контур NestJS может быть закрыт от прямого публичного доступа (доступен только через Nginx). Секретные ключи платежных шлюзов физически изолированы. Строгие Guard-интерцепторы и RBAC на уровне контроллеров. | **Хорошая, но требует высокой дисциплины**. При неосторожном использовании Server Actions или клиентских хуков есть риск случайного раскрытия внутренних эндпоинтов или утечки секретов. |
| **5. Удобство разработки админки (Admin DX)** | **Высокое**. Можно использовать специализированные готовые фреймворки (Refine.dev, React-Admin) или создать изолированную SPA-панель на базе Vite/React, работающую с чистым NestJS REST/OpenAPI, не смешивая кэши и стили с витриной. | **Среднее**. Приходится изолировать роуты админки внутри App Router (`/app/admin/*`), настраивать отдельные layouts и следить, чтобы кэширование Next.js не повлияло на динамические данные админки. |
| **6. Независимость Frontend и Backend** | **Полная**. Четкий контракт REST API / OpenAPI (Swagger). Фронтенд можно полностью переписать (например, на мобильное приложение iOS/Android), не трогая бизнес-логику бэкенда. | **Слабая**. Серверный код тесно связан с соглашениями Next.js (Server Actions, cookies, headers из `next/headers`). Повторное использование логики для мобильного приложения потребует рефакторинга в Route Handlers. |
| **7. Возможность расширения (Воркеры и Cron)** | **Отличная**. NestJS «из коробки» идеально интегрируется с очередями фоновых задач (BullMQ / Redis) для водяных знаков, сверки зависших платежей по расписанию (`@nestjs/schedule`), микросервисами и внешними интеграциями. | **Затруднительная**. В среде Next.js запуск постоянных cron-задач и фоновых очередей воркеров (Long-running processes) осложнен, требуется отдельный воркер-процесс или сторонние вебхук-триггеры. |

### 1.2. Экспертная рекомендация

> [!NOTE]
> **Предварительная рекомендация**:
> 
> Для проекта **LEKALO ZHIIDE** рекомендуется **Вариант А (Next.js + NestJS в рамках Monorepo)**:
> 1. Проект оперирует цифровыми активами, финансовыми вебхуками, фоновыми задачами сверки оплат (Reconciliation Cron) и потенциально тяжелыми процессами (обработка PDF, генерация превью). Выделенный бэкенд на NestJS гарантирует надежную работу постоянных планировщиков и изоляцию фонового воркера (BullMQ).
> 2. Формат монорепозитория (pnpm workspace / Turborepo) нивелирует сложность синхронизации типов: единый пакет `@lekalo/types` разделяется между фронтендом Next.js и бэкендом NestJS.
>
> *Альтернатива для сжатых сроков: Если ключевой задачей Адилета является минимизация времени и стоимости запуска MVP одним разработчиком (Медина) в кратчайшие сроки — **Вариант Б (Next.js Fullstack)** также технически реализуем при условии выноса cron-сверки платежей в отдельный легковесный скрипт на базе Node-cron.*
>
> **Окончательное решение принимается владельцем проекта (Адилетом).**

```

                           │ HTTPS / REST API / Cookies
┌──────────────────────────▼─────────────────────────────┐
│                      BACKEND                           │
│   NestJS (TypeScript) • Fastify/Express • BullMQ       │
│   Argon2id (Auth) • Class-Validator • Pino Logger      │
└──────────────┬──────────────────────────┬──────────────┘
```

### 2.1. Клиентская часть (Frontend)
- **Фреймворк**: **Next.js 15+ (React 19, App Router, TypeScript)**.
  - *Плюсы*: Server Components обеспечивают высокую скорость первичной загрузки страниц (LCP < 1.5 сек) и безупречное SEO для привлечения швейной аудитории через поисковые системы. Встроенная оптимизация изображений (`next/image`) автоматически конвертирует эскизы моделей в форматы WebP/AVIF.
  - *Минусы*: Механизм кэширования App Router требует явной инвалидации тегов (`revalidateTag`) при обновлении каталога.
- **Стилизация и UI-компоненты**: **Tailwind CSS + Shadcn UI (на базе Radix UI)**.
  - *Плюсы*: Высокая скорость верстки, отсутствие тяжелых CSS-библиотек во время выполнения (zero-runtime), адаптивность под мобильные устройства (смартфоны покупателей).
- **Управление состоянием**: **Zustand** (локальное состояние корзины и фильтров) + **TanStack Query** (кэширование и синхронизация серверных данных).

### 2.2. Серверная часть (Backend API)
- **Фреймворк**: **NestJS (TypeScript)**.
  - *Плюсы*: Строгая модульная архитектура, встроенная поддержка внедрения зависимостей (Dependency Injection), декораторы для валидации DTO (`class-validator`), автоматическая генерация документации OpenAPI (Swagger), отличная интеграция с очередями BullMQ.
  - *Минусы*: Дополнительный бойлерплейт по сравнению с плоскими экспресс-роутами.
- **Фоновые очереди задач**: **BullMQ + Redis**.
  - *Назначение*: Асинхронная отправка транзакционных email с чеками и ссылками, периодическая сверка зависших платежей по расписанию (раз в 10 минут), очистка устаревших гостевых сессий.

### 2.3. Слой данных и ORM
- **СУБД**: **PostgreSQL 16+**.
  - *Плюсы*: Строгое соответствие ACID для финансовых операций; поддержка бескомпромиссных внешних ключей и составных уникальных индексов (предотвращает создание вариантов-дубликатов); тип `JSONB` для сохранения снимков позиций заказа (`product_snapshot`).
  - **Денежные типы (Financial Precision)**: **Строгий запрет на float/double**. Все цены, суммы заказов, платежей и возвратов сохраняются в типе `NUMERIC(12,2)`. Все расчеты производятся в сомах с точностью до 1 тыйына (0.01 KGS).
- **ORM**: **Prisma ORM** (альтернатива: **Drizzle ORM**).
  - *Плюсы*: Декларативное и наглядное описание схемы данных (`schema.prisma`), полностью типобезопасный сгенерированный клиент, автоматические миграции без ручного SQL.

### 2.4. Аутентификация и безопасность Cookies
- **Архитектура**: **JWT (Stateless Access Token) + Stateful UserSessions в базе данных / Redis**.
  - Короткоживущий `accessToken` (15 минут) передается в заголовке `Authorization: Bearer` или куке.
  - Долгоживущий `refreshToken` (30 дней) хранится строго в защищенной куке: `HttpOnly`, `Secure`, `SameSite=Lax`.
  - **Важное обоснование `SameSite=Lax`**: Использование `SameSite=Strict` категорически не подходит для интернет-магазина с внешним эквайрингом. При возврате покупателя со шлюза банка на сайт магазина браузер выполняет cross-site переход; при `Strict` куки авторизации не будут переданы, и покупатель окажется разлогинен на экране успеха заказа. Значение `SameSite=Lax` обеспечивает надежную защиту от CSRF и гарантирует сохранение сессии при редиректе от банка.
- **Хэширование паролей**: **Argon2id**. Современный криптографический стандарт, защищенный от перебора на GPU/ASIC.

### 2.5. Хранение файлов и медиа
- **Объектное хранилище**: **S3-совместимое (Cloudflare R2 / AWS S3 / MinIO для local-dev)**.
  - *Публичный контур (Public S3 Bucket)*: фото моделей, эскизы, схемы раскладки лекал. Раздаются через глобальный CDN с кэшированием.
  - *Закрытый контур (Private Secure S3 Bucket)*: платные PDF-файлы выкроек и общие инструкции по пошиву. Публичный доступ закрыт наглухо (`Block All Public Access`). Выдача покупателям — строго через Presigned GET URLs с временем жизни 5–15 минут.
  - *Прямая загрузка (Presigned PUT URLs)*: администраторы загружают тяжелые PDF напрямую из браузера в S3-бакет, не нагружая оперативную память Node.js сервера.

### 2.6. Инструменты тестирования
- **Unit & Integration**: **Vitest + Supertest**.
- **End-to-End (E2E)**: **Playwright**. Сквозные тесты чекаута, оплаты и выдачи PDF.

### 2.7. Инфраструктура и развертывание
- **Контейнеризация**: **Docker & Docker Compose** (Node apps, PostgreSQL, Redis, MinIO).
- **Веб-сервер / Reverse Proxy**: **Nginx**. Терминация SSL (Let's Encrypt), сжатие Gzip/Brotli, маршрутизация (`/api` -> NestJS, `/` -> Next.js), Rate Limiting.
- **CI/CD**: **GitHub Actions**. Автоматическая сборка, линтинг, тесты и деплой на сервер по SSH.
